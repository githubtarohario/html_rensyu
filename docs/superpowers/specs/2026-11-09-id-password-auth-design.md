# ID・パスワード認証への変更 設計

## 背景・目的 (Intent)

[2026-11-07の設計](2026-11-07-user-login-score-design.md)では「パスワードなしのニックネーム方式」を選択していたが、この方式では誰でも他人のニックネームを名乗って得点を書き換えられてしまう。これを防ぐため、ログインをID・パスワードによる本人確認に変更する。

## ゴール (Goals)

- ニックネーム欄を「ユーザーID」として使い続け、パスワードによる本人確認を追加する
- 未登録のIDでログインを試みたときは、そのパスワードで新規登録として扱う（登録専用の別画面は作らない）
- パスワードはサーバー側でハッシュ化して保存する（平文保存はしない）
- 既存の得点記録・正誤判定・リーダーボードの仕組み（Task 1〜6で作ったもの）はそのまま使う

## 非ゴール (Non-goals)

- ID以外の表示名（ニックネーム）を別途持つ機能
- パスワードリセット・メール確認
- 得点送信など、ログイン後の各API呼び出し自体への毎回のパスワード要求（ログイン時にのみ確認し、以後は今と同じくクライアントを信頼する）
- ブルートフォース対策（レート制限等）、強力なパスワード強度チェック

## アンチゴール (Anti-goals)

- ログインが面倒になり気軽に使えなくなること（新規登録フォームを別に作らない、確認メールを入れない）
- 既存のスコア判定・問題データ・リーダーボードの仕組みを壊すこと

## 制約 (Constraints)

- 新しい依存ライブラリは追加しない。パスワードハッシュ化はNode標準の`crypto.scrypt`を使う
- 既存のUpstash for Redisをそのまま使う（`user:{id}:solved`等の既存キーはそのまま）

## 検討した作り方 (Approaches)

| 案 | 内容 | トレードオフ |
|---|---|---|
| A. IDをニックネームと同一視し、パスワードハッシュを追加 | 既存のキー設計（`user:{id}:...`）をそのまま使える | 最小限の変更で済む。別の表示名機能は持てないが非ゴールの通り不要 |
| B. ログインID（内部）と表示用ニックネームを分離 | 本格的なアカウント概念 | データモデル・UIとも複雑になり、今回の要望には過剰 |
| C. 外部認証サービス（Auth0等）を使う | 自前でパスワード管理をしない | 新しい外部サービス依存が増え、学習用サイトの規模には過剰 |

**選択: A**（本人承認済み）。既存の仕組みを壊さず、最小限の変更で本人確認を追加できるため。

## 決定した仕様 (Decided)

- **データ**: `user:{id}:passwordHash` に `scrypt$<saltHex>$<hashHex>` 形式の文字列を保存する新しいRedisキーを追加。既存の`user:{id}:solved`・`user:{id}:meta`・リーダーボードのキー設計は変更しない。
- **新API `POST /api/login`**: `{ id, password }` を受け取る。
  - そのIDのパスワードハッシュが存在しない → 新規登録として、渡されたパスワードをハッシュ化して保存し、ログイン成功を返す
  - 存在する → ハッシュと比較し、一致すれば成功、不一致なら401（IDとパスワードのどちらが間違っているかを区別しないメッセージにする）
- **既存API（`/api/score`・`/api/me`・`/api/leaderboard`）**: 変更しない。ログイン後はこれまでと同様にクライアントが保持するIDを信頼する
- **クライアント側**: ログインフォームにパスワード入力欄を追加し、送信時に`POST /api/login`を呼ぶ。成功したら（今の`saveNickname`と同様に）IDをlocalStorageへ保存し、既存のログイン後フロー（得点・正解済みマーク・ランキング更新）をそのまま実行する。失敗時はエラーメッセージを表示する
- **既存データ**: 本番に残っているテストデータ（ID "aaa"、パスワード未設定）は新方式ではログインできなくなるため、移行前に削除する

## ビルダーに委ねる部分 (Left to the builder)

- `POST /api/login`のレスポンス形式の細部（成功時に得点・解いた問題一覧も一緒に返すか、既存の`/api/me`呼び出しに任せるか）
- フォームのラベル文言・エラーメッセージの具体的な日本語表現
- パスワード入力欄のUI（表示/非表示切り替えボタンの有無など）
- パスワードの長さ上限など軽微な入力検証ルール
